# Порядок сборки

Дедлайн финальной сборки — 2026-10-29 10:00 UTC+3. После 28-го 20:00 логика не трогается.
Что не влезло в гейт дня — вычёркивается, а не переносится на 29-е.

## 1. Контракты (до кода)

- `TripRequest` со всеми полями + `FieldStatus`/`ConstraintKind`/`source`. Пока поля не
  зафиксированы, реестр зависимостей строить нельзя: `inputs` инструментов — это эти поля.
- `TripState` + версии.
- Реестр инструментов: `inputs`, `guard`, `cost`, политика ретраев.
- Коды нарушений и `severity`.
- SSE-события — зафиксировать файлом и отдать фронту. Это развязывает параллельную работу;
  если оставить на потом, фронт начнёт рендерить текст модели и потеряет `chosen`.
- Политика hard/soft и дефолтный набор hard-полей (их должно быть мало) + правило
  разрешения противоречий в требованиях.
- `Money` / `PriceLine` / `BudgetLedger` — до первого подсчёта суммы, иначе суммы в тексте
  и в state разойдутся.
- `POST /v1/runs/{run_id}/answers` идемпотентно и статус `run=interrupted` в БД: прерванный
  ход переживает рестарт процесса.
- Список терминальных исходов (`best_effort`, `infeasible`, `degraded`, `unsupported`) как
  часть ответа, а не как исключения.

Гейт: два человека команды могут по этим схемам писать код друг без друга.

## 2. Сквозной срез на mock-данных (главный шаг)

- Синтетический каталог: 8–10 направлений × 30–50 отелей, `synthetic=true`, плюс
  **`stay_rates` по ночам и `transport_legs` по датам** (seed-генерация, окно даты демо
  ±14 дней, сезонный коэффициент). Без календаря ставок пересчёт по сдвинутым датам
  невозможен, и ступень 1 не работает.
- Рантайм: узлы `state→state`, рёбра policy, checkpoint, interrupt (~200 строк).
- `PARSЕ` → `DECIDE` → `SEARCH` → `COMPOSE` → `VALIDATE` → `EXPLAIN` → `CHECKOUT`.
- Валидатор стыковок: прилёт vs дедлайн check-in, checkout vs отправление, трансферный
  буфер, соответствие ночей датам, вмещаемость, сумма и scope бюджета.
- **Один зелёный сквозной тест**: «хочу к тёплому морю в ноябре вдвоём с ребёнком, 150к,
  без долгих перелётов» → ≤2 вопроса → направления с числами → отели → план → корзина.

Гейт: проходится из CLI одной командой, время и число вызовов записаны в `run_id`-трейс.

## 3. Инкрементальность

- Реверс-индекс `поле → инструмент`, `affected()` с транзитивным замыканием.
- Ступени 0/1/2.
- Тест корректности инвалидации: «изменил `party.pets` → пересчитались ровно transport,
  hotels, transfer; destinations и weather не дёргались».
- Два кейса дельты с замером: «давай на троих», «у нас собака». Плюс ступень 0 на
  «бюджет −30%» — ноль вызовов инструментов.
- Кэш по content-hash аргументов.

Гейт: **сквозной сценарий проходит без сети** (все источники из локальной базы). Только
после этого добавляется что-либо из п.5.

## 4. Настоящие данные в подогреве

- Климат по месяцам → `climate_observations` (Open-Meteo, без ключа).
- Цены перелётов → кэш. Один легальный источник вместо скрейпинга.
- Пайплайн: payload → normalize → validate → dedup → entity + offer → index-text →
  embedding (при изменении текста) → provenance + `last_checked_at`.
- Статусы `verified / partially_verified / stale / unknown / synthetic` наружу, в карточки.

Внешние вызовы существуют только здесь, в nightly-подогреве. В демо-пути их нет.

## 5. Доказуемость корректности

- Number guard: числа из финального текста ↔ `TripState`, расхождение → перегенерация.
- Repair-петля: ≤2 итерации, маппинг `code→действие`, дедуп подписей, полная повторная
  валидация, сравнение версий.
- Лимиты хода + `budget_exhausted` как результат, а не как ошибка.
- Eval-набор 12 сценариев с инвариантами; метрики: доведённость, число уточнений, время до
  первой рекомендации, ошибки стыковок, fabricated-поля, repair success rate.
  **Определение «доведён до конца»** (без него метрика — слово, а не число): есть план с
  0 blocking-нарушений, пользователь перешёл в `CHECKOUT`, `BudgetLedger` сходится с
  итоговой суммой, в объяснении нет чисел, не найденных в state, и ни одно hard-ограничение
  не ослаблено без `user_approved`.
- Property-тесты композера: ни одна собранная поездка не превышает бюджет, стыковки
  неотрицательны, hard не ослаблен без `user_approved`.
- CI: pytest на mock-данных; падение доли соблюдения hard-ограничений блокирует merge.
- Трейс `run_id` + `make replay RUN=…` — офлайн-пересборка того же плана.
- Chaos-тест: убрать один источник → план возвращается с `stale`, без падения и без лжи.

## 6. Опциональное — только если гейт дня 3 пройден

- Мягкая релевантность через cross-encoder вместо LLM-скоринга.
- `JEVProvider` вторым бэкендом за `DecisionProvider` (не в критическом пути).
- Перенос узлов на `StateGraph` с checkpointer'ом — механический, потому что узлы чистые.
- Память между сессиями (`user_preferences`), пост-покупка, мобильная версия.

## 7. Финал

Сборка (Docker, миграции, seed), README с диаграммой и числами, запись золотого сценария,
структура питча: золото-путь → дельта-пересборка с числом вызовов → граница «модель/код» →
метрики eval → список неподтверждённого. И сравнение «обычный поиск vs агент» на одном
запросе — это буквально вопрос задания, отвечать надо в начале питча.
