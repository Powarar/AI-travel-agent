# Evidence

Сырые артефакты прогонов. Каждый файл — вывод скрипта, а не пересказ: числа в README
берутся отсюда и проверяются по `dataset_hash` / `prompt_version` / `metric_definition_version`.

Прогоны живого LLM платные и в CI не запускаются (`LLM_PROVIDER=mock`, `RUN_LIVE_EVALS`
не выставлен). Поэтому здесь лежат зафиксированные результаты прошлых живых прогонов,
а не «свежие» цифры, которые нечем воспроизвести бесплатно.

## Точность разбора запроса (слот №1)

Датасет `parse-ru-v1`, 20 кейсов, 37 обязательных полей, 55 проверок полей.
Модель `deepseek-v4.1-flash-1017`, `prompt_version=9cc7c100280d3a44`,
`metric_definition_version=parse-field-v2`.

| файл | дата (UTC) | обязательные поля | проверки полей | exact match | fallback | стоимость |
| --- | --- | --- | --- | --- | --- | --- |
| `parse-accuracy-2026-11-06-measured.json` | 2026-11-06 00:27 | 37/37 | 54/55 | 0.95 | 0 из 20 | 1.06374 ₽ |
| `parse-accuracy-2026-11-07-measured.json` | 2026-11-07 03:07 | 37/37 | 53/55 | 0.90 | 0 из 20 | 1.07814 ₽ |
| `parse-accuracy-2026-11-07-connect-timeout.json` | 2026-11-07 03:15 | 0/37 | 0/55 | 0.00 | **20 из 20** | 0 ₽ |

**Как это читать честно.** Два первых прогона измерены (`accuracy_status=measured`).
Третий — провал инфраструктуры: все 20 спанов имеют `status=error`, `error=ConnectTimeout`.
Модель не ответила ни разу, поэтому качество модели по этому прогону **неизвестно**, и
харнесс ставит `accuracy=null`, `accuracy_status=no_successful_model_samples`, а не «0%
точности». Подменять одно другим — значит врать в обе стороны: ноль обвинил бы модель в
том, чего она не делала, а замалчивание скрыло бы, что контур умеет падать.

`system_accuracy` в провале равен 0.909 — это доля полей, которые контур восстановил
детерминированно (defaults, вывод из дат), без модели. Он не является точностью модели.

Разброс exact match 0.95 → 0.90 между двумя измеренными прогонами на одном датасете и
одном промпте — это разброс модели, а не улучшение или деградация кода. Два прогона не
дают доверительного интервала; число приводится как есть, без «стабильно 95%».

`known_estimated_cost_rub` — оценка по прайсу известных моделей; `unpriced_calls` — число
вызовов, для которых цены нет. В провале `unpriced_calls=20` при нулевой стоимости:
вызовы не дошли до тарификации.

## Офлайн-базлайн на том же датасете

`parse-accuracy-2026-11-14-offline.json` — тот же `parse-ru-v1`, но `mode=offline`,
`model=deterministic-offline`: работает правило-ориентированный mock-провайдер, живых
вызовов нет, стоимость 0 ₽. 37/37 обязательных полей, 50/55 проверок, exact match 0.80,
fallback 0 из 20.

Это не точность LLM и не замена ей: цифра нужна как воспроизводимая точка отсчёта. Прогон
бесплатный и запускается в CI, поэтому по нему видно, что харнесс, датасет и метрика живы,
даже когда платных ключей нет. Разрыв с живыми прогонами (0.90–0.95 exact match) — вклад
модели поверх детерминированного разбора.

`async-e2e-2026-11-07.json` — 5 кейсов, `passed=5`, `functional_passed=5`,
`inventory="synthetic development catalogue"`. Это прогон HTTP-контура на синтетическом

## Браузерный прогон интерфейса

`demo-shots-2026-11-14.json` — отчёт `make demo-shots` (`web/scripts/demo-shots.mjs`,
headless Chromium через nginx на `:8080`). 11 шагов, `failedRequests=[]`, 8 скриншотов
в `docs/img/` (retina 2x).

| шаг | что проверено |
| --- | --- |
| `auth-screen` → `registered` | регистрация email+пароль, вход в приложение |
| `trip-request-sent` → два `question` | агент задаёт уточняющие вопросы, ответ идёт кнопкой |
| `plan-ready` | план с посчитанными суммами (`04-plan.png`) |
| `checkout` | заказ; в шаг подмешан один ответ `401` (`injected401=1`) |
| `session-resumed-after-reload` | перезагрузка страницы: сессия восстановлена, `refreshCalls=2` |
| `second-message-sent` → `plan-diff` | правка «Давай лучше в Сочи» → диф плана (`07-plan-diff.png`) |
| `logged-out` | выход, токены очищены |

`consoleErrors` содержит ровно одну запись — `401 (Unauthorized)` от подмешанного ответа.
Она ожидаемая: сценарий намеренно рвёт access-токен, чтобы показать тихое обновление и
повтор запроса. `failedRequests` пуст, то есть ни один запрос пользователя не потерян.

Что этот прогон **не** доказывает: он идёт на синтетическом каталоге и mock-провайдере,
поэтому проверяет контур и интерфейс, а не качество подбора отелей живой моделью.
SSE-транспорт в текущей реализации отдаёт готовый трейс прогона, а не потоковую генерацию;
скриншоты этого не отличают.

## Прогон CI

Первый запуск воркфлоу — PR #1, run
[43595141638](https://github.com/Powarar/AI-travel-agent/actions/runs/43595141638):
job `python` и job `web` — success. В CI поднят настоящий Postgres (`pgvector/pgvector:pg16`)
и выставлен `REQUIRE_TEST_DB=1`, поэтому интеграционные тесты не скипаются: `492 passed,
4 skipped` (skip — только live-гейт `RUN_LIVE_EVALS`), покрытие 87%, mypy strict — 74 файла
без замечаний, ruff без замечаний; `web` — `tsc --noEmit` и production-сборка. Цифры совпали
с локальным прогоном на mock-провайдере. Coverage XML выгружен артефактом `coverage-xml`.

## Чего здесь нет

- Нагрузочных цифр (RPS, p95 под нагрузкой): стенд не нагружался, чисел нет.
- Точности на продовом трафике: у продовых вызовов нет разметки, поэтому точность
  измеряется только на размеченных датасетах.
