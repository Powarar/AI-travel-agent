# Контракты

Фиксируется до кода. Контракт с фронтом — предмет договорённости 25-го, а не 28-го.

## TripRequest

Каждое поле несёт метаданные, а не только значение:

```python
class FieldStatus(str, Enum):        # unknown — не то же самое, что выдуманное значение
    KNOWN = "known"                  # сказал пользователь
    INFERRED = "inferred"            # выведено из контекста, требует подтверждения
    DEFAULTED = "defaulted"          # подставлен безопасный дефолт
    UNKNOWN = "unknown"              # неизвестно, решаем спрашивать или нет

class ConstraintKind(str, Enum):
    HARD = "hard"                    # молча не ослабляется никогда
    SOFT = "soft"                    # превращается в штраф в ranking
```

| Поле | Тип | kind по умолчанию | Примечание |
|---|---|---|---|
| `origin` | `str \| None` (город/IATA) | hard | unknown → один вопрос, дефолт опасен |
| `direction.mode` | `explicit \| open \| forbidden` | hard | `open` = единственный триггер INSPIRE |
| `direction.explicit` | `str \| None` | hard | |
| `direction.excluded` | `list[str]` | hard | |
| `dates.start` / `dates.end` | `date \| None` | hard | |
| `dates.flexibility_days` | `int` (0–7) | soft | unknown → 0, не выдумывать |
| `nights` | `int \| None` | hard | выводится из дат, не парсится отдельно |
| `party.adults` | `int` | hard | unknown → 2 + `DEFAULTED` |
| `party.children` | `list[int]` возрастов | hard | влияет на rooms и трансфер |
| `party.pets` | `bool` | hard | фильтрует hotels/transport/transfer |
| `budget.amount` / `.currency` | `Decimal` / `str` | hard | RUB по умолчанию для RU-запроса, `DEFAULTED` |
| `budget.scope` | `total \| per_person` | hard | частый источник конфликтов, уточнять при расхождении >2× |
| `budget.includes` | `set[transport, lodging, activities, transfer]` | hard | |
| `transport.modes` | `set[plane, train, auto]` | soft | |
| `transport.max_hours_direct` | `float \| None` | hard | «не хочу тратить много времени на дорогу» |
| `transport.prefer_direct` | `bool` | soft | |
| `transport.overnight_ok` | `bool` | soft | первое поле для дешёвого repair |
| `lodging.rooms` | `int` | hard | выводится из party |
| `lodging.stars_min` | `int \| None` | soft | |
| `lodging.budget_per_night_max` | `Decimal \| None` | soft | выводится из budget |
| `lodging.must` | `set[str]` (удобства) | hard | `pet_friendly` при pets=true |
| `themes` | `set[beach, city, nature, culture, food]` | soft | |
| `soft_preferences` | `list[str]` дословные фразы | soft | идут в `pref_text` для эмбеддинга |
| `identity.citizenship` / `residence` | `str \| None` | hard | **только** для флага `visa_required_for`, не для рекомендаций |

Не извлечённое поле остаётся `UNKNOWN`. Модель не имеет права подставлять значение без
`source="default"` — это отдельный тип ошибки в eval-наборе (fabricated field).

## Политика hard / soft

Жёсткость — это **не про точность значения**, а про то, разрешено ли нарушить поле ради
более привлекательного результата. Берётся из формулировки пользователя, а не из имени поля.

| Как появилось значение | `kind` / `status` | Отступление |
|---|---|---|
| Сказано явно: «в Италию», «150 000 на всё», «не больше 4 часов в дороге» | `hard` | никогда молча; только через вопрос |
| Сказано размыто: «атмосферный», «не слишком много туристов» | `soft` | да, штраф в ranking |
| Выведено из контекста: «вдвоём» из «с женой» | `inferred` | только после подтверждения пользователем |
| Подставлен дефолт: валюта RUB, `adults=2`, `flexibility_days=0` | `defaulted` | да; видно в UI как «предположено» |
| Системное/легальное ограничение | `hard`, не торгуется | вариант исключается из допустимого множества, не штрафуется |

По умолчанию **hard** только у: `dates.start/end`, `party.*`, `budget.amount|scope|includes`,
`direction.explicit` (если названо), `origin`, легальные флаги, `lodging.must`. Всё
остальное — `soft`. Причина: если hard-полей много, агент вечен в уточнениях; если мало —
молча подменяет сказанное.

`direction.mode`:

- `explicit` («хочу в Италию») → альтернативная страна никогда не подставляется молча; она
  идёт отдельным блоком «почему не Италия» с посчитанной разницей и только по согласию.
- `open` («куда-нибудь к тёплому морю») → ограничения нет вообще, это триггер INSPIRE.
- `forbidden` («только не Египет») → hard-исключение, фильтром.

**Конфликт hard-ограничений — это вопрос, а не решение агента.** Агент не знает, какое из
требований пользователь считает главным, поэтому спрашивает с уже посчитанными
компромиссами, после первого замера, а не заранее:

```
«В Италию, 7 ночей, вдвоём: минимум 168 400 ₽ — на 18 400 выше бюджета.
 1) остаться в Италии → отель 3* или −2 ночи
 2) уложиться в 150 000 → Албания / Тунис, вот чем отличаются
 3) поднять бюджет»
```

Отсюда правило repair: сначала ступени 0/1, затем targeted re-search, и только когда
нарушение `HARD_CONSTRAINT_UNSATISFIED` не снимается без изменения требования — `ASK` с
конкретикой. Ослабить hard ради «результат выглядит лучше» запрещено (инвариант №2).

### Budget-aware перебор финалистов (`direction.mode = open`)

Не влезло самое релевантное направление — это не «плана нет», пока в выдаче есть другие
финалисты. Порядок такой:

- финалисты идут по приоритету источника (он уже учитывает soft-предпочтения), и для каждого
  собирается план;
- направление, где ни один отель не влезает в `budget.amount`, отпускается дальше, а его
  минимальная сверхлимитная сумма уходит **предупреждением** (`BUDGET_EXCEEDED:warning` с
  `destination`, `over_by`, `hotels`), а не молча выбрасывается из поля зрения;
- если влезло — это и есть план, предупреждения остаются в `state.violations`, чтобы фронт
  мог показать «Дубай: 244 850 ₽, не подошли»;
- если не влезло ни одно — наружу идёт **самый дешёвый из собранных** план: валидатор по нему
  считает `over_by` и `reduce_lodging_to`, и отказ звучит как «ждали 150 000 ₽, вышло
  166 950 ₽, проживание можно урезать до 15 500 ₽», а не по самому дорогому просмотренному.

Hard-бюджет при этом не ослабляется ни на копейку: в план попадает только набор, сумма
которого `<= budget`. Мягкое предпочтение меняет лишь порядок перебора (инвариант №2). Для
`direction.mode = explicit` перебор не работает: названное направление не подменяется другим,
и отказ остаётся по нему (см. «Названное направление»).

## Названное направление (direction.explicit)

`direction.explicit` со `status=known` и `source="user"` — hard-требование, и у хода есть
ровно три легальных исхода:

1. **план в этом направлении** — `chosen.component_refs["destination"]` равен коду, к которому
   сворачивается названное слово;
2. **`HARD_CONSTRAINT_UNSATISFIED`** с `field_path="direction.explicit"`, `expected` = названное
   слово, `actual` = код выбранного направления — когда направление различимо и собран план
   в другом;
3. **`infeasible` с посчитанными числами** — когда названного направления в допустимом
   множестве нет вовсе (нет в каталоге, нет перелётов, нет ставок): в `expected/actual/evidence`
   обязаны быть числа — сколько направлений рассмотрено, сколько отсеклось по каждой причине.

Тихая подмена направления недопустима **ни при каком исходе**, включая `best_effort` и
`degraded`: «хочу в Сочи», закончившийся планом в Анталье с пустым списком нарушений, — это не
«не нашли совпадений», а скрытое отступление от hard-поля (инвариант №2). Проверка
принадлежит **валидатору** (`validation/coherence.py`, `docs/LLM-BOUNDARY.md`: «ревью
корректности требований — только код»), а не вежливости подборщика: источник вправе вернуть
то, что у него есть, и обязанность контура — не выдать это за выполненное требование.

Сворачивание названия к коду — словарь и транслитерация, не модель. Сверяются нормализованные
формы (регистр, посимвольная транслитерация, йотированная начальная «е», `х` → `kh`/`h`,
склейка и разбиение составного имени по дефису, усечение до двух последних букв падежного
окончания, словарь исторических латинских форм — 7 названий: `Moscow`, `Istanbul`, `Hurghada`,
`Saint Petersburg`, `Alanya`, `Paphos`, `Nha Trang`), и сравнение разрешено только как «равно»
или «одно начинается с другого» на длине ≥8. Вхождение в середину запрещено: в `novorossiysk`
основа «россия» стоит хвостом, и на свободном вхождении названный город находил бы половину
каталога. Название считается выполненным, если выбранный код попал в **множество** совпадений:
«в Турцию» удовлетворяется любой турецкой точкой каталога, а «в сочи» — только Сочи. Поля,
проверкой не охваченные: `direction.excluded` (исключение — фильтр источника, а не проверка
плана), `direction.mode` (режим, а не значение) и `unknown`-направление (нечему нечего
проверять). Опечатка в названии («Анталия») в совпадения не попадёт — это выход на исход 2
или 3, а не право источника угадать.

Второй край того же контракта: слово обязано **дойти** до `direction.explicit`, и это решает
разборщик слота №1 (`llm/slots.py`), а не модель. Кандидата «в/на + слово» отсеивает словарь
стоп-слов, и префикс в нём глушил название целиком: «тур» убивал «Турцию», «мар» —
«Мармарис», «гор» — «Горно-Алтайск», «дом» — «Доминикану». Такие формы сравнены целыми
словами (месяц, тема, «домой», состав «на двоих»), а непредсказуемые по падежу — стемом;
глагол поездки дополнен просьбой без движения («нужен тур в Египет»), иначе поле пустело и
исход 3 становился недостижим: вместо отказа по названной стране контур уходил подбирать
открытое направление. Промах в эту сторону — потерянное hard-поле, то есть тихая подмена;
лишнее слово, наоборот, даёт честный отказ, поэтому список стоп-слов расширять осторожнее,
чем сужать.

Ответ на вопрос про невыполненное направление (`ASK`, см. «Политика hard / soft») — это либо
новое название (пересборка с `suggest_destinations` по нему), либо «подбери сам»
(`mode=open`, `explicit=unknown`). Третьего нет: молча оставить прежний план с прежним
нарушением узел `apply_answer` не вправе.

## Чтение дат из русской речи

Разборщик один — `llm.schemas.range_days`, и его зовут все четыре пути: мок T-05, коэрсер
живой цитаты, узел ответа на вопрос и демо-скрипт викторины. Право на собственный разбор у
узлов нет: метрика слота №1 сравнивает мока и модель, а два разных плана на одной фразе
делают это сравнение бессмысленным.

* Формы: `2026-11-01 … 2026-11-08`, `28.10 - 05.11`, «с 28 октября по 5 ноября», «с 14 по 21»
  с якорем-месяцем. Якорь — уже известная дата заезда; без якоря и без слова месяца
  возвращаем `None`, и решение переспросить остаётся за `DECIDE`.
* День выезда меньше дня заезда ⇒ выезд в следующем месяце, а не пустая вилка: «с 28 по 5»
  при ноябре = 28.11 → 05.12, 7 ночей. Пустой диапазон — только равные границы («с 10 по 10»),
  и он `ValueError`, как и нечитаемый ответ.
* Когда в строке названы два месяца, каждый день берётся из своего: «с 30 октября по 3
  ноября» = 30.10 → 03.11.
* Промежуток по времени — не даты: «не больше 3 - 4 часов в дороге» даёт `None`, хотя месяц
  в разговоре известен. Различаем по слову после второго числа (час/ноч/минут/звёзд/дн/нед).
* «31 февраля» не выдумывается и не роняет ход: день прижимается к реальной границе месяца
  (`day_in_month`), потому что ответ пользователя не обязан быть календарно грамотным.
* ISO-вилка читается без слова «ноябрь» — в том числе моком: иначе детерминированный путь
  терял даты, которые живой путь находит.

## Money и учёт расходов

Деньги не `int` и не `float`:

```python
Money(amount: Decimal, currency: str)
PriceLine(kind: transport|lodging|transfer|activity|fee, amount, scope: total|per_person|per_night,
          included_in_budget: bool, source_id, fetched_at, data_status)
BudgetLedger(lines: list[PriceLine], total: Money, budget: Money, scope: BudgetScope)
```

Правила:

- `Decimal`, копеечный масштаб, округление **один раз** при итоговом подсчёте,
  `ROUND_HALF_UP`; промежуточные суммы не округляем.
- Городской/курортный сбор, топливный сбор, сервисный сбор, страховка — **отдельные
  `PriceLine`**, а не «прибавлено к цене», иначе пользователь не поймёт разницу.
- Пересчёт валют — только по курсу с `source_id` и `fetched_at`; при отсутствии курса —
  `UNKNOWN_CURRENCY`, не оценка на глаз.
- `budget.includes` решает, что попадает в итог: если `transfer` не включён, он всё равно
  показывается, но вне суммы и помечен «не учтён в бюджете».
- Двойной учёт ловится на уровне строк (одна и та же `PriceLine` не может попасть в
  `total` дважды) — это отдельный код нарушения `DOUBLE_COUNTED`.

Итог `BudgetLedger` — единственное место, откуда берутся числа для объяснения; guard сверяет
текст именно с ним.

## Противоречия в требованиях

Сообщение за сообщением пользователь может сказать «вдвоём» → «нас трое» → «с нами ещё
друг». Порядок разрешения:

1. Явное утверждение нового значения побеждает (`source=user`, `status=known`).
2. Поле, затронутое дважды с конфликтом, не «последнее wins» молча: создаётся
   `CONFLICTING_STATE` (warning) и поле помечается `needs_confirmation`.
3. Если противоречие задевает hard-поле и меняет результат — вопрос, с цитатой обоих
   значений («ранее: вдвоём, сейчас: трое — считаю трёх?»).
4. `inferred`, с которым пользователь не соглашается, понижается и не возвращается сам.
5. Любое изменение hard-поля пишется в `audit_events` со ссылкой на сообщение.


## TripState

```python
class TripState(BaseModel):
    trip_id: UUID
    version: int                     # растёт на каждый ход, никогда не мутируется on-place
    request: TripRequest
    stage: Stage                     # PARSE|CLARIFY|INSPIRE|SEARCH|COMPOSE|VALIDATE|REPAIR|SHORTLIST|COMPARE|EXPLAIN|PLAN|CHECKOUT
    candidates: Candidates           # destinations[], transport[], hotels[], transfers[]
    chosen: Basket                   # то, что пользователь подтвердил — не перезаписывается молча
    violations: list[Violation]
    repair_log: list[RepairAttempt]
    questions_asked: int
    budgets: RunBudget               # tool_calls, llm_calls, wall_clock, tokens
    provenance: dict[str, DataStatus]
```

История чата — не состояние. Важные решения живут в `TripState`, сообщения только
породляют `request`-delta. Это даёт: пересборку без «забыл, что мы уже выбрали отель»,
replay прогона и изменение одного компонента без потери остальных.

## Реестр инструментов

```python
Tool(
  name="hotel_search",
  inputs={"destinations", "dates.start", "dates.end", "nights",
          "party.adults", "party.children", "party.pets",
          "lodging.rooms", "lodging.stars_min", "lodging.budget_per_night_max",
          "lodging.must", "soft_preferences", "budget.includes"},
  guard=lambda s: bool(s.candidates.destinations) or not s.request.direction.explicit.is_unknown,
  guard_fields={"direction.explicit", "destinations", "dates.start", "dates.end"},
  output="candidates.hotels",
  cost="high",
  retries=3, backoff=(0.5, 1.0, 2.0), jitter=True, timeout=3.0,
  breaker=(failures=3, window=60), fallback="stale_cache",
  cache_ttl=3600,                              # по content-hash аргументов
)
```

| Инструмент | inputs (ключевое) | cost | fallback |
|---|---|---|---|
| `suggest_destinations` | month, party, transport.max_hours_direct, budget | med | stale-таблица |
| `weather_climate` | country, month | low | cache 7d |
| `transport_search` | origin, destination, dates, party | high | breaker → stale |
| `hotel_search` | destination, dates, party, lodging, soft_preferences | high | breaker → stale |
| `transfer_search` | destination, arrival_time, party, pets | low | default-оценка + `UNKNOWN` |
| `coherence_check` | (локально, без сети) | none | — |
| `checkout_mock` | basket, idempotency_key | none | идемпотентный повтор |

Направление в реестре называется `destinations` (в состоянии — `candidates.destinations`),
одна и та же строка фигурирует и в `provides` подборщика, и в `inputs` поиска. `guard` —
обычная функция над типизированным состоянием, не выражение в DSL (ADR-004).

`direction.explicit` входит в `watched` (**`inputs` ∪ `guard_fields`**) **всех четырёх**
инструментов, которым нужно направление: `suggest_destinations`, `weather_climate`,
`transport_search`, `hotel_search`. Разное место по-разному: у подборщика и климата поле
уходит в запрос к источнику (`inputs` — названное направление фильтрует каталог), у перелётов
и отелей оно в `guard_fields` (запрос идёт по уже resolved-`destinations`, а поле определяет
готовность). Смысл общий: названное направление меняет не только готовность запуска, но и
множество `destinations` — ответ на вопрос «а поедём туда-то» обязан переспросить подборщик, а
не пересобрать план поверх старых финалистов.

`affected(changed_fields)` = реверс-индекс полей + транзитивное замыкание вниз
(`compose` и `validate` — всегда downstream). Три правила замыкания:

- инструмент грязный, если дельта попала в `watched` = `inputs` ∪ `guard_fields`: поле либо
  уходит в запрос к источнику, либо меняет готовность запуска (`guard`);
- дальше замыкаем по `provides`: пересобранный `transport.arrival_time` тянет трансфер,
  пересобранные `destinations` — климат, перелёты и отели;
- инструменты с `cost="none"` (`coherence_check`, `checkout_mock`) в грязное множество не
  заносятся: к источнику они не ходят, а их локальный пересчёт — это и есть `validate`.

Общая `budget.amount` не входит в `inputs` поиска отелей: сумма — проверочное число
(`BudgetLedger`, T-03), а в запросе к источнику работает `lodging.budget_per_night_max`.
Иначе «бюджет −30%» на ступени 0 ложно объявлял бы отельный поиск грязным.

`dates.month` — производный аргумент (`nodes.stay_month`), не поле запроса: источник климата
ключуется одной парой `(dest_code, month)` (`data/seeds/climate.json`), а вилка «с 28 октября
по 5 ноября» ночует в двух месяцах. Берётся месяц с наибольшим числом ночей, при равенстве —
более ранний: пользователь называет именно его («в октябре»), и семидневная октябрьская
поездка не должна получать ноябрьскую температуру. `changed_fields` сравнивает множество
месяцев вилки, а не один выездной: сдвиг «28.10–05.11» → «01.11–08.11» оставляет выезд в
ноябре, а погоду меняет.

## Климат: месяц поездки и отсутствующее число

Факт погоды — `(code, month) → числа`, ровно по тому ключу, по которому его спрашивают
(`data/seeds/climate.json` = 61 направление × 12 месяцев). `month` обязателен в типе
`ClimateFact`, потому что без него прогон не различает «в октябре» и «в ноябре»: источник
выбрал бы строку наугад, а тест на это молчал бы.

```python
ClimateFact(code, month, day_temp_c: Decimal | None, sea_temp_c: Decimal | None,
            source_id, data_status)
```

- `day_temp_c` — воздух (в сиде `t_max`), `sea_temp_c` — вода. Оба **опциональны**: отсутствие
  числа оформляется как `None` → `unknown`, а не как `0` и не как «среднее по черноморскому
  побережью».
- Пробел данных, зафиксированный честно: в реальных строках климата (`source_id=
  open_meteo_archive`, `data_status=real`) морской температуры **нет ни в одном из 61
  направления**. Морскую воду показывает только тот источник, который её отдал (в офлайн-
  фикстурах золотого пути она есть), и карточка обязана назвать воздух и промолчать про море
  там, где числа нет.
- Молчание — не ошибка прогона: `ref["sea_temp_c"]` остаётся пустой строкой, `absorb` не
  пишет `"None"`, и объяснение не получает фразу про море. `unverified_numbers` сверяет текст
  с состоянием, поэтому выдуманная температура в нём — blocking-случай, а не «красивая цифра».
- `provenance["climate"]` берётся из `data_status` строк источника: `real` — подтверждено
  архивом, `synthetic` — наш генератор, смешение статусов в одном ответе даёт
  `partially_verified` (правило общее для всех срезов `candidates`).

## Что видит человек: подписи, пустые поля и порядок слотов

Строкой для человека считаются `ref["why"]` (причина финалиста), объяснение слота №5, тексты
вопросов и `refusal_text`. Правило одно: **подпись обязана называть то число, которое посчитано,
и молчать там, где числа нет**.

* Воздух и вода подписаны по-разному. `day_temp_c` — воздух (`t_max`), `sea_temp_c` — вода, и
  в каталоге воды нет; «+31.6 °C» рядом со словом «море» было бы неправдой, поэтому строка
  строится по presence-check: есть вода → «море +24 °C», нет → «воздух +31.6 °C», нет обоих →
  про погоду молчим вовсе.
* Месяц — по-русски (`shared/contracts/months.month_label`): `2026-11` это ключ источника, а
  не фраза. «Назовите вилку в 11-м месяце» и «воздух +30.8 °C в 2026-11» — обе строки читались
  как заглушка.
* Часов в дороге у направления **не бывает** двух видов: `ref["flight_h"]` — прикидка источника
  подбора, и в причине финалиста она так и подписана («перелёт 12.2 ч по данным подбора»), а
  объяснение плана берёт длительность собранных сегментов («перелёт 14.2 ч в одну сторону»).
  Без оговорки карточка спорила бы сама с собой.
* Слот №4 идёт **после** `weather_climate` (`runtime._collect`), а не сразу за подбором
  направлений: выбранная до погоды тройка осталась бы без температуры в причине — ровно того
  числа, ради которого направление и подбирали. Климат до выбора финалистов спрашивается на весь
  отбор (`destination_codes` без финалистов = все коды), число обращений к источникам от этого
  не меняется.
* Пустая строка в `ref` — это «не показывать», а не «показать пусто»: `est_total=""` не даёт
  карточке фразу «от », `flight_h=""` — фразу «перелёт ч». `source_id` (`geonames_bulk`,
  `open_meteo_archive`) — внутренний id провенанса, в пользовательских строках его нет; он
  нужен в логах, в `PriceLine` и в `provenance`.
* `ref["name"]` направления — написание источника (`data/seeds/destinations.json` хранит
  латиницу: «Sochi», «Pattaya»), а `country` — уже по-русски. Русского имени города у нас в
  данных нет, поэтому транслитерация остаётся на фронте, а не в контуре: выдуманное «Сочи»
  неотличимо от выдуманной температуры.
* Вопрос обязан быть читаемой фразой: между `why` и списком вариантов стоит граница
  предложений («…нечего искать в перелётах. Варианты: Москва, …»), а не склейка двух мыслей
  через пробел.
* У суммы две формы и обе — из `Money`: `as_display()` («150000 RUB») для машин (аргумент
  источника, лог, content-hash) и `as_ru()` («150 000 ₽») для всего, что читает человек,
  включая `expected/actual/evidence` нарушений: отказ собирает текст именно из них. Знак
  рубля приписывается только RUB — для остальных валют остаётся ISO-код, «$» за USD был бы
  той же подменой, что и температура, которой нет в данных.
* Guard сверяет числа **без пробелов с обеих сторон** (`unverified_numbers`): состояние
  хранит суммы уже человекочитаемой строкой, и сравнение «как написано» считало бы выдумкой
  число, которое положил туда сам код. На живом слоте №5 такая ложная находка стоит второй
  платной генерации и отката на шаблон.

## Источник на каталоге `data/seeds` (`--sources seed`)

Шесть сигнатур (`suggest_destinations`, `weather_climate`, `transport_search`, `hotel_search`,
`transfer_search`, `checkout_mock`) остаются теми же и возвращают те же типы — `registry.py`
и оркестратор не знают, чем их накормили. Флаг `--sources {fixture,seed}` в
`scripts/run_pipeline.py`, **дефолт — `fixture`**: золотой путь T-05 меряется на фикстурах,
и подменять их каталогом в том же прогоне нельзя, иначе цифры приёмки слотов станут
несопоставимы.

Правило одного уровня со «числа считает код»: **ни одного числа на глаз**. Чего нет в строке
каталога — того нет в выдаче (`None` → `unknown`, пустая строка в `ref`), и это видно в
карточке и в `provenance`.

Что вывод, а не факт источника, и как это названо:

* Обратного сегмента в `data/seeds/transport_legs.json` нет (3788 строк, все «туда»,
  2026-11-01…2026-11-30). `_pair` даёт зеркало прямого: те же минуты, то же время суток вылета,
  дата — конец вилки, `leg_id` с суффиксом `-ret`, `overnight` считается по датам вылета и
  прилёта. Цена обратного = цена прямого из той же строки. Статус и `source_id` наследуются от
  прямого сегмента, потому что «обратного рейса в данных нет» — это про расписание, а не про
  подтверждённость цены.
* Прилёт обязан быть **в день заезда** (или раньше): рейсы на более поздние даты отсекаются до
  выбора, иначе план на «14–16» везёт туриста в отель 17-го.
* Направление отсекается по `transport.max_hours_direct` по тому же числу минут, что и перелёты
  (`min_flight_minutes()`), а не по оценке «примерно 5 часов».
* `hotels.json` не содержит вместимости: `HotelSpecs.capacity = None`, и `_hotel_fits` тогда
  пропускает проверку состава. Это дыра данных, а не разрешение на выдумку: `OCCUPANCY_EXCEEDED`
  на seed-источниках не проверяется, и в отчёте прогона это называется.
* `transfers.json` = одна строка на отель (`trf-<hotel_id>`), поэтому `TransferOffer.hotel_id`
  заполнен, и `compose` требует трансфер **этого** отеля: пришить гостинице путь от аэропорта
  соседней — значит собрать план из двух разных поездок.
* Климат ключуется парой `(code, month)`; `sea_temp_c` в сиде нет ни у одного из 61 направления
  (см. секцию «Климат»).
* Ставки есть только на 2026-11-01…2026-12-07: «в октябре» на seed-источниках даёт `infeasible`
  с числами, а не подстановку ноябрьских ставок.
* **Каталога нет — прогон встаёт до первого запроса.** `seed_sources()` и `catalog()` вызывают
  `require_catalog()`, а `run_pipeline.py` печатает оператору строку-инструкцию и выходит с
  кодом 2. Молча взять фикстуры вместо отсутствующего `data/seeds` нельзя: прогон мерил бы
  чужой набор строк и называл его каталогом. Проверка стоит до сборки слотов, потому что
  падать из первого инструмента — значит сжечь платный запрос слота №1.
* Час прилёта в сиде не сдвинут на разницу поясов: во всех 3788 строках `arr_at` =
  `dep_at + duration_min` по стенным часам, поэтому у рейсов восточнее вылета прилёт показан
  раньше, чем он местный (SVO→ALA: 04:45 вместо 06:45), и фильтр `_reaches_checkin` из-за
  этого пропускает пару рейс+отель, которую на реальных часах не пустила бы. Это дыра данных
  (её правит `data/generators/flights.py`, а не источник), и источник её молча не пересчитывает:
  число «на глаз» в плане выглядело бы починкой, а осталось бы выдумкой. Метка пояса при этом
  честная: `arr_tz = \N` (68 сегментов Иссык-Куля) берёт зону самого направления из
  `destinations.json`, а не `+00:00`.

Состав направления (упорядочено по релевантности финалистов):

* `_reaches_checkin(рейс, отель, трансфер)` = `прилёт + 30 мин буфера + минуты трансфера ≤
  дедлайн заселения`. Буфер — **то же число**, что читает валидатор
  (`arrival_buffer_min`): сборка не имеет права «чинить» стыковку, которую проверка не видит.
* Если ни один рейс направления не успевает ни в один подходящий отель, направление **пропускается**,
  а не отдаётся планом с заведомым нарушением: `for destination in _finalists(state)` копит
  отказы в `failures` и продолжает. Отдаётся первый отказ — он относится к самому релевантному
  направлению, и его числа полезнее остальных.
* Каждый срез `SearchResult` несёт счётчики в `meta` («направлений в каталоге», «рейсов в выдаче»,
  «отелей на направление», …). Пустая выдача без счётчиков читалась бы как «финалистов нет» без
  объяснения, поэтому `refusal_text` собирает отказ по-русски из `expected`/`actual`/`evidence`
  blocking-нарушений плюс счётчики по отказавшему срезу. `infeasible` без чисел — нарушение
  контракта, а не стилевая шероховатость.
* Повтор прогона на том же входе обязан давать тот же JSON. Поэтому `checkout_mock` на каталоге
  хеширует **корзину**, а не все аргументы: `idempotency_key` рантайм берёт из `run_id`, а это
  случайный UUID, и с ним заказ переставал повторяться. Различаются только часы
  (`wall_clock_ms`, замеры слотов) и `trip_id`, который UUID по контракту.
* Название направления разбирается и латиницей: `data/seeds/destinations.json` пишет города
  по-английски («Gelendzhik»), и если бы слот №1 принимал только кириллицу, слово терялось бы до
  состояния — валидатор сверяет `direction.explicit`, а пустое поле сверять не с чем, и на месте
  отказа пользователь получил бы план чужого города.

## Ступени эскалации дельты

| Ступень | Действие | Вызовов | Пример |
|---|---|---|---|
| 0 | пере-ранжировать уже найденных | 0 | «бюджет −30%» |
| 1 | пересчитать выбранный план на новых входных | 0–1 | «на троих» влезает ли в номер |
| 2 | re-search только грязных инструментов | 2–3 | «у нас собака» |
| 3 | расширить поиск (другие даты/направление) | 5+ | только с разрешения, если задевает hard |

Ступени 0 и 1 не обращаются к источнику вовсе: `tools_for(changed, step)` отдаёт пустое
множество, пересобираются только порядок, выбранный план и проверки. С какой ступени
начинать ход, считает `entry_step(changed)` по реестру; дальше поднимает repair-цикл (T-08).
Ступень 3 в `EscalationStep` нет — расширение поиска с разрешения появляется только после
зелёного гейта T-05.

## Коды нарушений

`severity ∈ {blocking, warning, suggestion}`. Только blocking останавливает выдачу плана.

| code | severity | repairable | действие |
|---|---|---|---|
| `BUDGET_EXCEEDED` | blocking | да | ступень 0 → `transport.overnight_ok`, дешёвые отели |
| `HARD_CONSTRAINT_UNSATISFIED` | blocking | зависит | если hard и не решается ступенями → **вопрос**, не ослабление |
| `ARRIVAL_AFTER_CHECKIN_DEADLINE` | blocking | да | трансфер / более ранний рейс / ранний заезд |
| `CHECKOUT_BEFORE_DEPARTURE` | blocking | да | сдвиг даты выезда |
| `TRANSFER_GAP_TOO_SHORT` | blocking | да | другой рейс или трансфер |
| `OCCUPANCY_EXCEEDED` | blocking | да | смена номера/отеля |
| `PET_NOT_ALLOWED` | blocking | да | фильтр `pet_friendly` |
| `CANDIDATES_EMPTY` | blocking | да | расширение, затем вопрос |
| `UNKNOWN_AVAILABILITY` | warning | да | пометить `unknown`, не выдавать за подтверждённое |
| `STALE_SOURCE` | warning | нет | показать дату проверки |
| `CONFLICTING_SOURCES` | warning | нет | обе цены + источник |
| `LEGAL_UNKNOWN` | warning | нет | «нужна проверка на официальном источнике», запрет на статус «подтверждённо» |
| `FABRICATED_FIELD` | blocking | нет | ошибка парсера → повтор с feedback |

Каждое нарушение: `expected`, `actual`, `affected_component`, `evidence`,
`suggested_actions` — из этого репейер берёт вход, а фронт рисует «что не так».

`HARD_CONSTRAINT_UNSATISFIED` ставится за отступление от **сказанного** hard-поля, и
`field_path` обязан называть это поле: `party.pets`, `budget.amount`,
`transport.max_hours_direct`, `direction.explicit`. Для направления проверка односторонняя:
валидатор не решает, подходит ли Сочи под «тёплое море», он отвечает только на «совпал ли
код плана с названным словом» (числа и причины отсева — у `CANDIDATES_EMPTY` из сборки).

## SSE-контракт с фронтом

Фронту **не отдаётся текст как источник истины**: отдаётся `TripState` + поток событий,
текст — подпись к событию.

```
run_started          {run_id, trip_id}
phase_changed        {from, to}
llm_call             {slot, ms, tokens_in, tokens_out}      # опционально, для демо трейса
tool_started         {tool, args_hash, from_cache}
tool_completed       {tool, ms, count, status}
tool_failed          {tool, attempt, policy, will_retry}
question             {field, text, options[], allow_skip}   # ← interrupt оркестратора
candidates           {kind, items[], ranking_factors}
violation            {code, severity, expected, actual, affected_component}
repair_started       {violation_code, action_signature, iteration}
plan_updated         {version, changed_components[], kept_components[]}
answer_text          {block_id, text, numbers_verified}
checkout_completed   {order_id, idempotent_replay: bool, simulated: true}
budget_exhausted     {limit_hit, best_effort_version, unresolved[]}
```

## HTTP и возобновление после interrupt

```
POST   /v1/trips                          → trip_id
POST   /v1/trips/{id}/messages            → run_id, контент-тип text/event-stream
GET    /v1/trips/{id}/state?version=N     → TripState
POST   /v1/runs/{run_id}/answers          → возобновление прерванного хода
GET    /v1/runs/{run_id}                  → трейс фаз (для replay и для отладки)
POST   /v1/trips/{id}/checkout            → Idempotency-Key
```

Ход, остановленный на вопросе, живёт в БД как `run(status=interrupted, awaiting=field[])`,
а не в памяти процесса: перезапуск API не должен терять начатый разговор. Ответ на вопрос
идемпотентен по `(run_id, field)` — двойная отправка кнопки не создаёт второй ход и не
сдвигает `version` дважды. Фронт обязан уметь отрисовать «ожидает ответа» по `state`, а не
по наличию текста в ленте.

## Терминальные исходы (не исключения)

Каждый ход заканчивается одним из статусов, и все они — валидный ответ пользователю:

| Статус | Когда | Что видит пользователь |
|---|---|---|
| `plan_ready` | 0 blocking, violations = warnings | план + что не подтверждено |
| `awaiting_answer` | конфликт hard-ограничений или значимый unknown | вопрос с посчитанными компромиссами |
| `best_effort` | лимиты хода исчерпаны | лучший допустимый вариант + список неисследованного |
| `infeasible` | допустимое множество пусто и расширение невозможно без изменения требований | почему именно не складывается, по строкам `BudgetLedger`/ стыковок |
| `degraded` | источник лежит, выдаём stale | план + дата проверки + `stale` на затронутых полях |
| `unsupported` | запрос вне продукта (визовые гарантии, оплата, обход ограничений) | что мы не делаем и куда смотреть официальный источник |

`infeasible` и `best_effort` обязаны содержать **числа**, объясняющие отказ: какая строка
бюджета какая, до скольки нужно снизиться. «Не нашлось вариантов» без цифр — это провал на
невиданном запросе, а жюри будет давать именно их.

## Мягкая релевантность (слот №3)

Исполняется cross-encoder'ом (`/rerank`), а не чат-моделью: «атмосферный» не выражается
полем, и скоринть его LLM-вызовом дороже, чем один запрос к реранкеру
(`docs/LLM-BOUNDARY.md`, таблица 6 слотов — «не LLM по возможности»).

```python
def soft_relevance(self, query: str, documents: dict[str, str]) -> dict[str, float] | None
```

* `query` собирает код: `pref_text` плюс слова `themes` переводом (`beach` → «море пляж»),
  потому что реранкер понимает русский, а enum-значение — нет.
* Слова к `Theme` — одна таблица `schemas.THEME_WORDS` на оба разборщика (детерминированный
  мок T-05 и `apply_deltas` над ответом модели), как `month_of` для дат. Со своей таблицей в
  `slots.py` мок знал «море» и «морю», но не родительный «у моря»: `themes` оставались
  неизвестны, `query` — пустой, runtime пропускал слот №3 (`if not documents or not query`),
  и план вызовов показывал `SL-3 = 0` на сообщении, которое явно просит атмосферный отель.
  Молча неоплаченный слот — лучший исход; хуже него прогон, за который заплатили и ничего
  не измерили.
* Живой разбор добирает мягкие поля у детерминированного парсера (`schemas.top_up_soft_fields`),
  только если сам не вернул ни `themes`, ни `soft_preferences`. Снято живым прогоном 2026-10-28
  (`--repeat 9`, `--sources seed`): модель отдавала `themes` в 2 ходах из 9, и в остальных
  `/rerank` не вызывался уже по причине «пустой запрос от живого слота №1». Граница ровно та:
  добираются поля без чисел, hard-поля не читаются и не пишутся, `used_fallback` остаётся
  `False` (метрика модели не портится), а `ParsedMessage.soft_top_up` делает сам факт добора
  видимым числом в sweep'е.
* Таймаут вызова — 5 с, а не 2.5: бар `p95 ≤1 с` в таблице приёмки мерился на трёх документах,
  а каталог даёт 40–64 строки. На 40 документах основная модель отвечает 1.5–1.8 с, запасная —
  до 4.2 с, и при 2.5 с обе падали в таймаут. Две попытки подряд (2 × 5 с) обязаны влезать в
  `wall_clock` хода — это проверяется тестом, а не комментарием.
* `documents` — индексируемый текст кандидата под его `candidate_id`: название, звёзды,
  направление, удобства. Ключом, не позицией: сопоставление ответа с входом делает клиент,
  порядок в ответе перепутать нельзя.
* `None` — слот выключен, ключа нет или источник не ответил. Тогда порядок кандидатов
  остаётся тем, как его отдал `hotel_search`: доступность внешней модели не должна влиять на
  воспроизводимость трейса прогона.
* Число кладётся в `ref["relevance"]` кандидата отеля **после нормализации в пределах одного
  вызова** и округления до 0.05. Нормализация обязательна, потому что шкала у cross-encoder'ов
  своя: один отдаёт 0.001–0.02 на русских текстах, другой 0.3–0.5. Сырое число без приведения
  легло бы в один bucket с нулём, и слот №3 перестал бы менять план, оставаясь оплаченным.
  Минимум вызова → 0.05, максимум → 1.00, между ними линейно, затем шаг 0.05. Нижняя граница
  0.05 не случайна: у неоценённого кандидата балла нет, и `_hotel_order` читает за него 0.0 —
  значит оценённый обязан остаться выше, даже когда модель скорит почти нулём.
* Если все скоры вызова равны, каждый получает 0.50: различимого сигнала нет, и среди
  кандидатов снова решает стоимость ночи.
* `score` источника не перезаписывается: в состоянии остаются оба числа, и видно, что
  именно добавил слот №3.
* Разделение по ролям, а не по шкале: `score` — **детерминированный приоритет источника**
  (на каталоге `data/seeds` это монотонная функция от `t_max` месяца поездки: «теплее» выше),
  а не утверждение «эта модель сочла кандидата релевантным». Мягкое предпочтение пользователя
  выражает только слот №3 (отели) и слот №4 (три направления с причиной). Поэтому приоритет
  обязан: (а) быть вычисленным из реальных строк каталога, (б) не выходить в текст карточки как
  оценка модели, (в) уступать, когда `ref["relevance"]` есть. Офлайн-прогон остаётся на
  приоритете намеренно: иначе состав плана зависел бы от доступности сети.
* Отель в `compose` выбирается по ключу `(-relevance, стоимость ночи)` **среди вариантов, при
  которых план влезает в бюджет**: мягкое предпочтение важнее цены среди подходящих, а
  превышение бюджета по-прежнему ловит валидатор — мягкое поле не превращается в тихий отказ
  от пожелания. Порядок именно такой, потому что `budget` — hard-поле: мягкий балл не имеет
  права делать выполнимый запрос невыполнимым (измерено живым прогоном 2026-10-27: поднятый
  реранком отель дал 183 300 ₽ при бюджете 150 000 ₽, и ход закончился как `infeasible`, хотя
  дешёвый подходящий отель был). Если не влезает ни один вариант, берётся лучший по баллу, и
  `BUDGET_EXCEEDED` выходит наружу числами — ничего не подменяется молча.
* Когда самый релевантный отель отвергнут из-за бюджета, его название кладётся в
  `facts["cheaper_than_relevant"]`: уступка soft-полю обязана называться в объяснении, а не
  пропадать.
* Когда `relevance` нет ни у одного кандидата, ключ сводится к цене — ровно то поведение, на
  котором зелёны тесты T-05.
* В `budgets.llm_calls` слот №3 не входит: лимит шести обращений — это чат-слоты. В
  `budgets.tokens` его токены считаются, потому что стоимость хода должна быть видна из
  состояния, а не только из логов.
* Отсечка `budgets.tokens` — счётчик провайдера на момент старта хода (`Run.tokens_seen`), а
  не ноль: один `LLMSlots` обслуживает и следующий ход, и весь `--repeat`. Живой прогон
  2026-10-28 показал лесенку 7 257 → 14 504 → 62 246 токена, где каждый ход оплачивал все
  предыдущие; в проде это два запроса пользователя, из которых второй вчетверо дороже первого.

### Как слот №3 замеряется и что видно до первого платежа

Предмет приёмки — качество порядка отелей и время одного обращения, поэтому `MeasuredSlots` в
`scripts/run_pipeline.py` кладёт в `slots[]` два числа, а не строку: `docs` (отелей на каждый
вызов) и `reordered` (отличился ли порядок ответа от порядка входа). «Ранжировали и переставили»
и «ранжировали, порядок тот же» — разные результаты, и по заметке «5 отелей» между прогонами их
не различить.

План вызовов `--dry-run` считает бесплатным прогоном моков T-05 на том же сообщении и тех же
`--answer`, а не строкой «примерно по одному»: форма хода от модели не зависит, поэтому на
`--repeat` числа умножаются ровно. Нет ответа на вопрос во флагах — план обрывается на этом
вопросе и говорит об этом отдельно (дорасти его выдуманным ответом значило бы недооценить слоты
после вопроса). Стоимости в плане нет: наружу отдаётся число обращений, а ₽ к нему прикладывается
своей таблицей — цен в репозитории нет.

Preflight той же команды проверяет ключ, `LLM_BASE_URL` и модель каждого слота и выходит кодом 2
до конструирования провайдера: `httpx.Client` с пустым `LLM_API_KEY` или `model=""` собирается
молча и падает на первом запросе, то есть посреди уже оплаченного хода. Значение ключа при этом
не печатается никогда — только «задан» и длина.
