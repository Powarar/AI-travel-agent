# Правила проекта — читать перед каждой задачей

AI travel agent для О! Хакатон 2026, трек «О!дин запрос». Стек: Python 3.11+, FastAPI,
Pydantic v2, PostgreSQL + pgvector, Alembic, pytest, asyncio. Frontend — Next.js, его ведёт
П2; П1 frontend-папку не трогает.

## Пайплайн работы с этой задачей

1. В чат агенту кидается **этот файл целиком** + `agent/CONTRACTS.md` + ровно **один** блок
   задачи из `agent/TASKS.md` (текст из поля «Текст для вставки»).
2. Из `docs/` агенту дают только раздел, на который ссылается блок (`docs/ARCHITECTURE.md`
   §2/§5/§7/§9/§15, таблица 6 слотов из `docs/LLM-BOUNDARY.md`). Остальное — человеческий
   слой: `docs/adr.md`, `docs/PLAN.md`, `README.md` агенту не кидать, там отвергнутые
   альтернативы и расписание, он читает их как открытые решения.
3. Если блок упёрся в контракт — сначала правка `agent/CONTRACTS.md`, потом код, одним
   коммитом.
4. Коммит содержит только файлы, названные в блоке. Приёмка — команды из блока, а не
   ощущение агента.

## Роли

| Роль | Зона | Что ведёт |
|---|---|---|
| П1 | агентский трек | `models/`, `orchestration/`, `tools/`, `composition/`, `validation/`, `repair/`, `llm/`, `decisions/`, грейдеры и метрики в `evaluation/` |
| П2 | данные, HTTP, окружение, экран | `data/`, `retrieval/`, `ranking/`, `api/`, `db/migrations/`, `docker-compose.yml`, `Makefile`, CI, `frontend/`, json-сценарии в `evaluation/` |

Формулу ранжирования и набор признаков утверждает П1 в `agent/CONTRACTS.md`, реализует П2.
Правило разделения: файл принадлежит одной роли. Чужое незакоммиченное изменение не
переписывать; если нужно его задеть — сначала вопрос в общем чате, потом правка.
Единственное общее — `backend/app/models/`: пишет П1, читает П2.

## Три инварианта (нарушение = переделать, а не обосновать)

1. `TripState` — единственный источник истины. История сообщений только порождает delta
   требований. Никаких решений, живущих в тексте чата.
2. Hard-ограничения не ослабляются молча: ни ранжированием, ни repair, ни моделью.
   Нарушение hard → вопрос пользователю с посчитанными компромиссами или `infeasible`.
3. Модель не считает и не утверждает факты. Цены, суммы, даты, стыковки, availability —
   только из кода и из источников с provenance.

## Граница «модель / код»

Модель ровно в 6 слотах: parse → `TripRequest`-delta; формулировка ≤2 вопросов; мягкая
релевантность; выбор 3 финалистов из проффильтрованных; текст объяснения; diff при
пересборке. Всё остальное — код: хватит ли данных, какие инструменты звать, SQL-фильтры,
скоринг, стыковки, сумма, выбор repair-действия. `LLMProvider`-интерфейс обязателен, чтобы
провайдер менялся одной строкой конфига.

## Жёсткие технические правила

- Деньги: `Money(Decimal, currency)`, `PriceLine`, `BudgetLedger`. Никаких `float`, никаких
  `int` «в рублях». Промежуточные суммы не округлять, итог — `ROUND_HALF_UP` один раз.
- Даты/стыковки: `datetime` с явной TZ-политикой; арифметика только в `validation/`.
- Catalog ≠ offer: `hotel`/`activity` — характеристики без дат; цена и условия живут в
  `stay_rates` / `transport_legs` / `offers`. Не прилеплять цену к каталогу.
- Каждое предложение несёт `source_id`, `fetched_at`, `data_status`
  (`verified|partially_verified|stale|unknown|synthetic`) и `synthetic`-флаг.
  `unknown availability` не становится подтверждённым по умолчанию.
- Инструмент описан в реестре: `inputs`, `guard`, `cost`, `retries`, `backoff`, `timeout`,
  `fallback`, `cache_ttl`. Новая сетевая операция без записи в реестр — не делать.
- Никакого скрейпинга чужих сайтов. Внешние вызовы только в nightly-подогреве; в
  демо-пути их нет, всё из локальной базы и кэша по content-hash аргументов.
- Не выдумывать API, поля, библиотеки, цены и правовые требования. Если факт не проверен —
  написать проверкой или спросить, а не подставить правдоподобно.
- Лимиты хода — константы в одном месте: ≤6 LLM-вызовов, ≤12 tool-вызовов, ≤20 с, ≤2
  вопроса, ≤2 repair-итерации. По исчерпании — `best_effort`, не исключение.

## Конвенции кода

Логи и идентификаторы — английский; пользовательские строки и HTTP `detail` — русский.
Комментарии только там, где непонятно почему; пересказ кода комментарием не делать.
Стиль — читаемый и плоский: без преждевременных абстракций, без классов-обёрток «на будущее»,
без fallback'ов для сценариев, которые не могут произойти. Не добавлять функциональность
сверх формулировки задачи. Ошибки — типизированные, не `except Exception` в бизнес-логике.

## Чего не делать, даже если «казалось бы полезно»

Не трогать frontend-папку, если задача не про API-контракт. Не вводить нового
фреймворка оркестрации без явного решения в задаче. Не добавлять Legal/визовый слой,
solver, мультиагентов, RRF-фьюжн, память между сессиями — они отложены в
`docs/ARCHITECTURE.md` §15. Не менять контракты из `agent/CONTRACTS.md` молча: если
нужно — сначала предложить правку, потом код. Не переписывать чужие незакоммиченные
изменения.

## Как оформлять готовность

Задача считается сделанной, когда: тест проходит локально; `mypy` без новых ошибок;
изменения не вышли за файлы, названные в задаче; если задет контракт — обновлён
`agent/CONTRACTS.md`.
